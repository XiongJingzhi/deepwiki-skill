# 模块文档组件规范

> 本文件是所有文档组件的单一真实来源，包含每个组件的：
> - 触发条件、格式变体、降级方案、所需上下文
> - 源码追溯要求（内联在各组件内）
> - 生成规范（写法细节与示例）
>
> **章节标题全局规则**：所有组件的 H2 章节标题必须根据模块的实际功能语义命名，禁止直接使用组件名（如"概述"、"核心逻辑"、"公开接口"、"内部结构"、"执行流程"、"数据流"等）。每个组件下方提供的"标题示例"是语义化标题的参考，而非固定标题。

---

## 文档语言

读取项目 `.deepwiki/config.yaml` 中 `generation.language` 的值（`zh` / `en` / `both`）：

| 值 | 文档语言 |
|----|---------|
| `zh` | 所有文档使用中文撰写（章节标题、正文描述、表格内容、注释说明）。代码标识符、专有名词、Mermaid 节点标签保持原文。 |
| `en` | All documentation in English. |
| `both` | 每个概念/描述先中文后英文（`中文描述 / English description`），代码标识符保持原文。 |

**默认值**：若 `config.yaml` 不存在或未设置 `generation.language`，默认为 `zh`。

## P0 — 必需组件

### relevant-source-files — 相关源文件

**触发**：必需（所有模块页面，无条件）
**位置**：页面顶部，H1 标题之后第一个区块；不要在它前面放摘要、分隔线、概述或表格
**格式**：`<details open>` 折叠块（带 `open` 属性，默认展开），内部使用目录+文件缩进树形列表；不使用表格或其他形态
**所需上下文**：模块核心文件列表、`public_interfaces` 的 `line/end_line`、`core_source_ranges`、`parse-results.json / code-structure.json.definitions`
**降级**：无（本组件不可省略）
**源码追溯**：本组件本身即为源码追溯入口，无需额外引用

**生成规范**：
- summary 标题：中文文档固定为 `相关源文件`，英文文档固定为 `Relevant source files`
- 列出 3–10 个本页最相关源码文件，目录节点只写目录名（带 `/` 后缀），文件节点缩进
- 每个文件项：**必须**带行号范围的 `file://` 链接（格式 `[文件名](file:///路径)`）+ 简短描述；
- 行号来源：优先使用 `generation-plan.json` 中 `source_files[].ranges` 提供的 `start_line`/`end_line`；ranges 为空时从 `module-analysis.json` 中 `core_source_ranges` 和 `public_interfaces.line/end_line` 推导
- 每个文件可拆为多个条目（不同行范围对应不同职责），而非一个文件只有一个链接
- 链接文本只显示文件名，不含行号

```markdown
<details open><summary>相关源文件</summary>

- [目录名/](file:///路径/)
  - [文件名.ext](file:///路径/文件名.ext) — 简短描述

</details>
```

### overview — 概述

**触发**：`CodePurpose not in [Test]`
**格式**：2–3 段文字 + 架构位置说明；可含 Mermaid flowchart 高亮当前模块（可选）
**所需上下文**：模块名和路径、CodePurpose、依赖关系、核心职责列表
**降级**：无
**源码追溯**：不要求（概述为叙述性内容）

**生成规范**：
- 用 2–3 段描述模块的目的、解决的问题、核心价值
- 说明模块在整体系统架构中的角色和层级位置
- 标题语义化：不要写"概述"，应根据模块功能命名，如"认证模块概述"、"数据管道概览"

---

### design-rationale — 设计思路

**触发**：`CodePurpose in [Entry, Agent, Service, Api, Command, Database]`，或模块复杂度 >= 30，或 `key_insights` 非空
**格式**：
- 设计目标
- 约束条件
- 当前方案
- 替代方案与取舍表：`| 方案 | 收益 | 代价 | 为什么当前没选 |`

**所需上下文**：`module_summary`、`key_insights`、`risk_points`、`extension_points`、核心源码片段
**降级**：若设计意图无法从源码直接确认，标注为"推断"并说明证据来源
**源码追溯**：不要求，但推断必须注明依据（文件名/调用关系/注释/接口形状/依赖方向）

**生成规范**：
- 先讲目标和约束，再讲实现；不要一开始就贴代码
- 明确区分"源码事实"和"设计推断"
- 标题示例："为什么采用事件驱动架构"、"配置设计的取舍"

---

### code-walkthrough — 核心逻辑

**触发**：必需（所有模块页面，无条件）
**降级**：模块逻辑极简单（如纯常量导出、类型别名）时，可降级为 3-5 行关键代码片段 + 一句话说明
**格式**：
- 格式 A：精简版核心源码（伪代码或裁剪代码，10–30 行）+ 目的说明
- 格式 B：Source 链接（`file://...#Lx-Ly`）+ 带中文注释的关键源码片段（20–80 行，可拆 1–3 段）+ 逐段讲解表格
- 格式 C：关键变量/分支/调用/错误路径说明 + 设计取舍
- 格式 D：对比讲解（重构/优化场景）

**所需上下文**：完整函数代码（或截断后保留重要行）、函数签名和参数说明、调用关系、模块主路径或关键扩展点、关键变量/分支/错误路径、源码文件路径与 `start_line/end_line`
**降级**：若源码过长，先给精简伪代码/裁剪片段，再说明省略了哪些非关键细节；不要整文件搬运
**源码追溯**：**必需** — 每段真实源码片段前必须写 `**Source:** [path](file:///path)`，代码块内容必须与该文件对应

**格式选择规则**

| 场景 | 格式 |
|------|------|
| 主路径复杂但可抽象 | 先给精简版核心源码或伪代码，再给关键说明 |
| 代码可划分为 2-5 个逻辑块 | 带注释源码片段 + 逐段讲解表格 |
| 代码逻辑连贯，难以分块 | 带注释代码 + 关键变量/分支/调用说明 |
| 重构/优化场景 | 对比讲解 |

**生成规范**：
- 先给精简版核心源码（10–30 行伪代码/裁剪代码），概括主执行路径，让读者先看懂骨架
- 再给 1–3 段真实源码片段（每段 20–80 行），添加中文注释解释关键变量、分支、调用、状态变化、错误处理
- 代码块后必须提供逐段讲解表：`| 片段 | 做什么 | 为什么这样做 | 关键变量/调用 | 风险 |`
- **核心逻辑必须有真实代码讲解**（可抽象或精简），不得只有概念描述
- 允许为讲解添加中文注释，但不得改变源码语义；省略非关键代码时用 `// ...` 或 `# ...` 明确标注
- 章节名自适应：根据模块实际功能命名，示例："配置加载与校验逻辑"、"认证与鉴权核心流程"、"缓存读写与失效策略"
