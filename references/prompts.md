## 代码深度分析

分析代码文件，提取完整的语义信息：

```
深度分析以下代码文件：

文件: {{ FILE_PATH }}
语言: {{ LANGUAGE }}
完整代码内容:
{{ CODE_CONTENT }}

预提取的文档注释（由 extract_docs.py 生成）:
{{ EXTRACTED_DOCS }}

### 语言术语规范

根据文件扩展名检测源语言，使用对应的术语：

| 语言 | 扩展名 | 函数/方法术语 | 文档注释风格 |
|------|--------|---------------|-------------|
| JavaScript/TypeScript | `.js` `.ts` `.tsx` | function | JSDoc (`/** */`) |
| Python | `.py` | function | docstring (`"""`) |
| Java | `.java` | method | Javadoc (`/** */`) |
| C# | `.cs` | method | XML doc (`///`) |
| Go | `.go` | function / method | `//` comments |
| Rust | `.rs` | fn | `///` / `//!` doc comments |

### 文档注释提取

- **JS/TS/Python/Java/C#**：从文档注释（`/** ... */`、`"""..."""`、`/// ...`）中提取文档。保留 `@param`、`@returns`、`@throws`、`@deprecated` 标签。
- **Go**：从导出标识符前的 `//` 注释中提取文档。注意 `// Deprecated:` 注解。示例：`// NewClient creates a new client...` 文档化 `NewClient`。按导出标识符分组；将 `// Deprecated:` 映射为已弃用状态。
- **Rust**：从 `///`（条目文档）和 `//!`（模块文档）注释中提取文档。保留 `# Examples` 代码块、`# Panics`、`# Errors`、`# Safety` 章节。将 `#[deprecated]` 属性映射为已弃用状态。

### 分析原则

- **优先使用预提取结果**：`EXTRACTED_DOCS` 已从源码中提取了签名、参数、返回值和示例，以它为基础进行语义补充，避免重复提取或遗漏。
- **解释 WHY 和 HOW**：不只描述代码做了什么（WHAT），更要解释为什么这样设计（WHY）和如何实现的（HOW）。
- **区分事实与推断**：直接从代码中观察到的信息标记为事实，推断的设计意图标记为推断。

请进行 **全面深度分析**，输出以下信息：

## 1. 模块概述
- **核心职责**：详细描述模块解决什么问题，为什么需要这个模块（3-5 句）
- **设计理念**：采用了什么设计模式/架构思想，为什么这样设计
- **在系统中的位置**：与其他模块的关系，在整体架构中扮演什么角色

## 2. 公开接口（每个接口详细说明）
对于每个导出的函数/类/类型：
- 名称、签名、行号
- **详细描述**：做什么、怎么做、什么场景使用（不少于 2 句）
- **参数说明**：每个参数的含义、约束、默认值
- **返回值说明**：返回什么、可能的值、错误情况
- **注意事项**：边界情况、性能考量、常见错误

> 注意：使用示例留在模块文档和 API 文档中生成，此处不需要。

## 3. 内部实现（帮助理解代码逻辑）
- **核心算法/逻辑流程**：用 Mermaid flowchart 展示
- **关键数据结构**：内部使用的重要数据结构
- **状态管理**：如果有状态，说明状态变化

## 4. 依赖关系
- **内部依赖**：依赖哪些项目内模块，为什么依赖
- **外部依赖**：使用哪些第三方库，用来做什么
- **被依赖**：哪些模块依赖本模块

## 5. 扩展性与维护
- **如何扩展**：添加新功能的推荐方式
- **潜在改进点**：可以优化的地方
- **测试建议**：关键测试场景

输出格式：结构化 YAML，包含上述所有字段。仅输出 YAML 内容，不要混入 Markdown 格式。
```

## 生成原则

1. **条件章节**：参考 templates.md 中模块模板的条件标注，仅生成适用的章节。不满足条件的章节直接跳过。
2. **内容密度优先于章节完整性**：宁可写好 5 个相关章节，也不要凑满 9 个空壳章节。
3. **模块文档侧重设计理念**：解释"为什么这样设计"，内部实现逻辑和数据流。"接口签名和使用示例"由 API 文档承担。
4. **代码示例使用项目主要语言**：将 `{{ IMPORT_STATEMENT }}` 替换为该语言的惯用导入语句。

## 生成要求

### 1. 概述（必需）
- 用 2-3 段文字描述模块的目的、解决的问题、核心价值
- 说明模块在整体系统架构中的角色
- 包含架构位置图（Mermaid flowchart，高亮当前模块）

### 2. 核心类与函数（条件：模块包含 class/struct/interface/enum 定义）
- 核心特性表格：| 特性 | 说明 | 相关接口 |
- **classDiagram**：展示核心类/接口的属性、方法、关系
  ```mermaid
  classDiagram
  class ClassName {
    +property1 : Type
    +method1(param : Type) : ReturnType
  }
  ClassName --> RelatedClass : 依赖
  ```
- 图表来源引用
- 若模块无类/接口定义，跳过此章节。

### 3. 文件结构（条件：模块包含 2 个以上源文件）
- 列出每个文件及其职责（不只是文件名）
- 用表格呈现：| 文件 | 职责 | 导出内容 |
- 若模块只有 1 个源文件，用一句话说明即可。

### 4. 公开接口（必需）
- 接口总览表：| 接口 | 类型 | 描述 | 源码 |
- 对每个公开接口说明：签名 + 源码链接、参数表格、返回值说明
- 若模块类型定义丰富，在此处列出类型字段表格

### 5. 代码示例（条件：模块复杂度 ≥ 低 或公开接口 ≥ 1 个）
- 示例数量根据模块复杂度调整：
  - 简单工具模块（1-2 个函数）：1 个基础示例
  - 中等模块（3-5 个接口）：2 个示例（基础 + 进阶）
  - 复杂模块（6+ 个接口或含状态管理）：3 个示例（基础 + 进阶 + 错误处理）

### 6. 依赖关系（条件：模块有内部依赖或被其他模块依赖）
- 依赖关系图（Mermaid flowchart LR）
- 依赖说明表：| 依赖模块 | 用途 | 耦合程度 |
- 若模块完全独立，用一句话说明即可。

### 7. 错误处理（条件：模块定义了自定义错误类型、或函数包含错误返回值）
- 错误类型及触发条件表
- 调试技巧
- 若模块不涉及错误处理，跳过。

### 8. 相关文档（必需）
- 架构文档链接、API 参考链接、相关模块文档链接

## 依赖关系分析

> 对应 SKILL.md 第 5 步：在深度阅读源码后执行，将孤立的文件分析转化为连贯的架构依赖图。

```
根据以下代码洞察生成 **项目依赖关系图**：

高优先级文件洞察（importance_score >= 0.6）:
{{ HIGH_PRIORITY_INSIGHTS }}

每条洞察格式：
[组件名] | [角色标签] | [文件路径] | [重要性评分] | [复杂度] | [依赖项列表]

## 分析要求

请生成一份结构化的依赖关系分析，包含以下三个部分：

### 1. 核心依赖关系（core_dependencies）

列出项目中最重要的模块间依赖边，每条依赖包含：
- **from**：来源模块/文件名（不含路径前缀）
- **to**：目标模块/文件名
- **type**：依赖类型，必须为以下之一：
  - `Import` — 文件级导入（use/import/require 语句）
  - `FunctionCall` — 运行时调用依赖
  - `Inheritance` — 类继承/接口实现（extends/implements）
  - `Composition` — Has-a 结构（字段持有、组合关系）
  - `DataFlow` — 数据流动（API 载荷、共享状态、消息传递）
  - `Module` — 模糊依赖（当上述类型均不确定时使用）
- **importance**：重要性 1-5（5 最重要，基于被依赖频率和模块重要性评分）
- **description**：一句话描述依赖原因（可选）

### 2. 架构分层（architecture_layers）

将所有组件按架构层次归组，每层包含：
- **name**：层名称（如"展示层"、"业务逻辑层"、"数据访问层"、"基础设施层"）
- **level**：层级数字，数字越小越接近基础设施（1 = 最底层）
- **components**：属于该层的组件名列表

### 3. 反向依赖映射（reverse_dependencies）

为每个模块列出**依赖它的模块**，用于增量更新时的变更传播：

\`\`\`json
"reverse_dependencies": {
  "模块A": ["模块B", "模块C"],
  "模块D": ["模块A"]
}
\`\`\`

### 4. 关键洞察（key_insights）

3-5 条自由文本的架构观察，重点关注：
- 核心枢纽模块（被多个模块依赖的组件）
- 潜在的循环依赖（A 依赖 B，B 又依赖 A）
- 架构边界违规（跨层调用）
- 高耦合模块（依赖数量 > 10）

---

## 输出格式

严格按以下 JSON 结构输出，不要包含任何 JSON 以外的内容：

\`\`\`json
{
  "core_dependencies": [
    {
      "from": "模块A",
      "to": "模块B",
      "type": "Import",
      "importance": 4,
      "description": "模块A 通过 import 依赖模块B 的工具函数"
    }
  ],
  "architecture_layers": [
    {
      "name": "业务逻辑层",
      "level": 3,
      "components": ["service_a", "service_b"]
    }
  ],
  "reverse_dependencies": {
    "模块A": ["模块B", "模块C"],
    "模块D": ["模块A"]
  },
  "key_insights": [
    "utils 模块是核心枢纽，被 12 个模块依赖，建议拆分",
    "发现潜在循环依赖：auth_service → user_service → auth_service"
  ]
}
\`\`\`

**注意事项**：
- 依赖类型必须严格使用上述 6 种之一，不要创造新类型
- importance 必须是 1-5 的整数
- level 必须是正整数
- 如果 description 内容不确定，可省略该字段
- 最多输出 50 条 core_dependencies，按 importance 降序排列
- reverse_dependencies 必须包含所有被至少一个模块依赖的组件
```

## 置信度标注规范

> **核心原则**：让 AI 对每条断言标注"证据来源"和"置信度"，区分事实与推断。

### 置信度等级定义

| 等级 | 符号 | 定义 | 证据来源 |
|------|------|------|---------|
| **高置信** | 🟢 | 断言直接来自源码或文档注释 | 源码行号、docstring、JSDoc、注释 |
| **中置信** | 🟡 | 断言从代码结构推断 | 类继承关系、方法签名、导入语句 |
| **低置信** | 🔴 | 断言从命名约定或常见模式推断 | 变量名、文件名、目录结构 |

### 标注规则

**规则 1：高置信断言必须附带源码引用**
```markdown
该模块使用观察者模式实现事件分发。

**证据来源**：
- ✅ 直接来自代码：`src/event/Observer.ts:12-25` 定义了 `Observer` 接口

**置信度**：🟢 高
```

**规则 2：中置信断言必须说明推断依据**
```markdown
模块似乎实现了缓存机制。

**证据来源**：
- ⚠️ 从代码结构推断：存在 `cache` 字段（`src/store/Cache.ts:5`）和 `invalidate()` 方法（`src/store/Cache.ts:45`）

**置信度**：🟡 中

> ⚠️ 此推断基于代码结构，未找到明确的架构文档说明。
```

**规则 3：低置信断言必须标注"待确认"**
```markdown
该模块可能是配置管理模块。

**证据来源**：
- ⚠️ 从命名推断：目录名为 `config/`

**置信度**：🔴 低

> ⚠️ 待确认：建议检查模块内的实际代码逻辑。
```

**规则 4：禁止无证据来源的高置信断言**
```markdown
❌ 错误示例：
该模块是整个系统的核心，负责所有业务逻辑。
（无证据来源，无法验证）

✅ 正确示例：
该模块负责用户认证流程，包括登录、登出和令牌刷新。

**证据来源**：
- ✅ 直接来自代码注释：`src/auth/service.py:5` docstring
- ✅ 从代码结构推断：存在 `login()`, `logout()`, `refresh_token()` 方法

**置信度**：🟢 高
```

### 输出优先级

生成文档时，按以下优先级呈现内容：
1. **高置信内容**：优先展示，作为文档主体
2. **中置信内容**：展示但标注"推断"
3. **低置信内容**：折叠或标注"待确认"，不影响主体阅读
