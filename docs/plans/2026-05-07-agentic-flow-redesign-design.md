# DeepWiki Agentic Flow Redesign

Date: 2026-05-07

## Goal

Redesign DeepWiki from a script-defined analysis pipeline into an agentic documentation workflow.

The new model should reduce deterministic preprocessing, remove the AST-heavy compilation chain from the main path, and let the Agent explore, understand, plan, and generate documentation with lightweight script support.

## Selected Approach

Use a full new contract for the first agentic version.

Old cache files and pipeline stages will no longer define the main workflow. Preview, finalization, quality checks, and other end-user utilities can remain, but the core generation path moves to new artifacts and simpler phases.

The implementation should start from a clean project root. The current DeepWiki implementation is moved under `legacy/old-pipeline/` as an archived reference. New work is built in fresh root-level `SKILL.md`, `scripts/`, `schemas/`, `references/`, and `tests/` directories instead of gradually editing the old pipeline in place.

This avoids carrying old workflow assumptions through file names, tests, helper APIs, and cache contracts.

## Main Workflow

The new main path is:

```text
init-wiki
→ prepare-inventory
→ agentic-analysis
→ plan-pages
→ generate-menu
→ generate-pages
→ finalize-wiki
```

### Stage A: Preparation

Preparation only initializes `.deepwiki/` and collects directory-level facts.

It generates `cache/project-inventory.json` with:

- Project name and root path
- File tree summary
- Ignore rules
- File classifications
- Language and framework hints
- Package manager hints
- Candidate entry files
- Important config files
- Existing docs
- Basic size and count statistics

This stage does not run AST parsing, call graph extraction, module semantic analysis, or skeleton generation.

### Stage B: Agentic Analysis And Planning

The Agent reads `project-inventory.json`, explores source files as needed, and writes:

- `cache/semantic-analysis.json`
- `cache/page-plan.json`

`semantic-analysis.json` captures the Agent's project understanding:

- Project purpose
- Architecture model
- Runtime flows
- Reader-facing concepts
- Semantic modules or themes
- Cross-cutting concerns
- Risks
- Extension points
- Source evidence

Module boundaries are semantic and do not need to match directories.

`page-plan.json` is the only page planning artifact. It replaces both the old `doc-topology.json` and `generation-plan.json`.

Each page includes:

- `page_id`
- `title`
- `output_path`
- `page_type`
- `purpose`
- `source_targets`
- `depends_on`
- `status`

The plan also includes `sections`, `generation_order`, and `menu_seed`.

### Stage C: Page Generation

Documentation is generated page by page from `page-plan.pages[]`.

Before writing each page, the workflow creates `cache/page-context/<page_id>.json`. This context can be built by an Agent, a helper script, or a mix of both.

Each page context includes:

- Page objective
- Relevant source files
- Source excerpts
- Related pages
- Claims to cover
- Symbols or files that should be linked
- Page-specific constraints

Page generation can run serially or in parallel. The task boundary is the page, not the old module-analysis unit.

### Finalization

Finalization keeps only checks tied to the final wiki output:

- Generate or reconcile `wiki/menu.json`
- Generate or reconcile `wiki/doc-map.md`
- Fix Mermaid syntax
- Validate Mermaid when the local toolchain supports it
- Run Markdown quality checks
- Check links
- Run necessary consistency checks

The old `validate-analysis` and `evidence-index` gates are removed from the main path. Evidence shifts to page context and source links.

## New Cache Contract

The main cache contract contains four groups:

### `cache/project-inventory.json`

Produced by `prepare-inventory`.

It stores low-interpretation facts only. It does not store AST, function signatures, call graphs, or deep module analysis.

### `cache/semantic-analysis.json`

Produced by the Agent.

It stores the project mental model and semantic decomposition. Important claims should include source evidence with file paths and optional line numbers.

### `cache/page-plan.json`

Produced by the Agent.

It is the single source of truth for the wiki menu seed, page list, generation order, and page-to-source mapping.

### `cache/page-context/<page_id>.json`

Produced per page before generation.

It is the direct input to page writing and the traceable basis for later quality checks.

## Retired Main-Path Artifacts

These old artifacts are no longer generated by or required for the main path:

- `cache/structure.json`
- `cache/parse-results.json`
- `cache/code-structure.json`
- `cache/architecture-skeleton.json`
- `cache/module-analysis.json`
- `cache/doc-topology.json`
- `cache/generation-plan.json`
- `cache/evidence-index.json`
- `cache/modules/*/context.json`

They may remain temporarily as legacy implementation details during migration, but the Agent-facing workflow should not depend on them.

## Error Handling

Preparation failure stops the workflow and reports the unreadable path, permission problem, or invalid ignore configuration.

Low-confidence semantic analysis does not automatically fail. The Agent records `confidence: low` and `open_questions[]` in `semantic-analysis.json`.

Page planning cannot proceed to generation until every page has `page_id`, `title`, `output_path`, and non-empty `source_targets`.

Single-page generation failures are recorded in `state/progress.json`. The workflow continues with other pages, retries failed pages once, and fails finalization if any page still fails.

If source evidence is insufficient, the page may be generated in a reduced form, but it must clearly identify which areas lack source evidence. The workflow must not invent APIs, call chains, or runtime behavior.

Finalization failure stops the workflow and reports the exact failed check and page.

## Testing Strategy

Keep or adapt tests for:

- `.deepwiki/` initialization
- Menu generation and reconciliation
- Finalization
- Wiki serving
- Mermaid repair and validation
- Markdown quality checks
- Link checks

Add tests for:

- `prepare-inventory` ignore handling
- File classification
- Language and framework hinting
- Entry candidate detection
- `semantic-analysis` schema validation
- `page-plan` schema validation
- Duplicate `page_id` detection
- Invalid `output_path` detection
- `page-context` creation
- End-to-end smoke flow with a small fixture project

Delete or mark legacy tests for:

- `extract_structure`
- `generate_skeleton`
- `prepare_module_context`
- `module_discovery`
- `validate_analysis`
- `evidence_index`
- Old `plan_doc_topology`

## Migration Notes

The first implementation should archive the current implementation under `legacy/old-pipeline/`, then recreate only the new root-level files needed for the agentic workflow.

Legacy scripts can remain in `legacy/old-pipeline/` for reference, but they should not be imported by the new implementation or listed as part of the main workflow. If a legacy behavior is still needed, reimplement the minimal version in the new root rather than depending on the archived pipeline.

The final design principle is:

> Scripts collect facts and verify output. The Agent understands, plans, and writes.
